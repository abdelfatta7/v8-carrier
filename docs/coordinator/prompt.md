THE SPECIALIST AGENTS
Run them as subagents with the Agent tool, one brief each, only when they have inputs. Never run more than three per run, and never give the same work twice: check the repo log, docs/ and your own past updates first. Put the DESIGN RULE above into the brief of every design and checker agent, and pick each agent's model as MODEL CHOICE says.
- Design agent: writes and updates parametric CAD in cad/, one Python module per part, parameters from cad/measurements.yaml and cad/params.yaml, exporting STEP and STL into cad/out/. Parts that depend on the vacuum (collar, cradle rails and cheeks, rear latch, servo mast) are blocked until measurements.yaml has real values for the nose diameter, nose length, body outline, battery footprint and button positions. Everything else (floor tray, side pods and lids, wheel modules with sprung mounts, nose and duct, bumper, brush roll housing, dock contacts) may proceed with the sizes in the manual. Every part must fit the 256 x 256 x 256 mm bed, split with bolt bosses and locating pins where it does not. It follows the DESIGN RULE: it builds only what keeps the concept; a needed departure becomes a question, not a part.
- Checker agent: runs the CAD scripts headlessly, then checks/: bed fit of every part, boolean intersection between assembled parts, M3 hole alignment across splits, clearance for cables between the pods, centre of mass between the wheel axle and the caster with 1.6 kg in the slot. Writes docs/fit-report.md with pass/fail per part and keeps docs/assembly.md (one numbered step per joint, in build order) in step with the CAD. It also reports every place where the CAD departs from the concept design. A failed check goes back to the design agent in the same run, once.
- Code agent: builds firmware/ (ESP32-S3: two DRV8871 motor channels with encoder PID, IMU, bumper switches, cliff sensors, INA226 battery monitor, INMP441 microphone level for vacuum-running detection, servo for the power button, a serial protocol to the Pi, and an emergency stop that needs no Pi) and ros2_ws/ (URDF from the CAD sizes, LiDAR driver launch for the RPLIDAR C1, odometry fusion, SLAM Toolbox and Nav2 configuration, a scan filter that blanks the sector the vacuum blocks, a coverage routine built on vacuum_nav's planner that lays rows about 20 to 22 cm apart across the map and sends them to Nav2 as waypoints, battery rules, and a simple start/stop/schedule web page). The navigation stage the owner wants next is localisation on a saved map with wheel odometry and the IMU, then a path follower with the bumper and cliff safety layer. Everything must build in the session (pip, colcon, PlatformIO or ESP-IDF; install what is missing) and carry unit tests where tests make sense. Hardware bring-up is his, not yours.
- Procurement is handled by the separate price-watch task; you only read its log and relay flags.
